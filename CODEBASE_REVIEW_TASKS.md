# Предложенные задачи по итогам обзора кодовой базы

## 1) Исправление опечатки
**Задача:** привести к единому имени сервис планировщика: `planer-agent` vs `planner-agent`.

- В репозитории директория и docker-сервис называются `planer-agent`, но в README несколько раз указан путь `planner-agent`.
- Минимально безопасный вариант: исправить README на текущее фактическое имя.
- Более структурный вариант: переименовать директорию/сервис в `planner-agent` и обновить все ссылки.

## 2) Исправление ошибки
**Задача:** убрать постоянное подключение к БД из `ExecuteSQLAgent.__init__` и перейти на подключение «на запрос» (или пул соединений).

- Сейчас соединение создаётся один раз при старте процесса и хранится в `self.connection`.
- При разрыве соединения (рестарт БД, idle timeout, сетевые проблемы) последующие запросы будут стабильно падать до рестарта сервиса.
- Нужна стратегия переподключения: `psycopg2.pool` или создание/валидация соединения в `execute_sql`.

## 3) Исправление документации/несоответствия
**Задача:** синхронизировать README с фактическими метками классификатора.

- В README описаны цели `sql`, `chart`, `both`, `other`.
- В `planer-agent` классификатор реально возвращает `search`, `chart`, `both`, `insert`, `other`.
- Нужно обновить описание API-ответа и секцию «Как работает», чтобы клиентам не приходилось угадывать актуальные значения `goal`.

## 4) Улучшение тестов
**Задача:** добавить базовые unit-тесты для критической SQL-логики и маршрутизации.

- В репозитории нет автотестов.
- Приоритетный минимум:
  1. тесты `ExecuteSQLAgent.safe_execute` (разрешённые SELECT, запрет опасных запросов, rollback при ошибке);
  2. тесты ветвления в `planer-agent /plan` для `search|insert|chart|both` с моками внешних HTTP-вызовов.
- Это снизит риск регрессий в основной бизнес-цепочке (классификация → SQL → визуализация).
